# Changelog

Todos los cambios notables a este proyecto se documentan aquí.

El formato sigue [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) y este proyecto adhiere a [SemVer](https://semver.org/spec/v2.0.0.html).

Cada entrada se documenta en **español** y **english**.

## [Unreleased]

### Fixed
- ES: **`nz_get_view_ddl` ahora devuelve DDL re-ejecutable** — antes devolvía solo el cuerpo SELECT de la vista (`_V_VIEW.DEFINITION`), sin el encabezado `CREATE VIEW … AS`, por lo que copiar el resultado no recreaba la vista. Ahora devuelve el DDL completo `CREATE OR REPLACE VIEW schema.view AS\n<cuerpo>`, con schema y vista en mayúsculas, igual que `nz_get_table_ddl`. `tools-contract.md` actualizado. Cierra #303.
- EN: **`nz_get_view_ddl` now returns re-executable DDL** — it previously returned only the SELECT body from `_V_VIEW.DEFINITION`, without the `CREATE VIEW … AS` header, so the output could not be used to recreate the view. It now returns the complete `CREATE OR REPLACE VIEW schema.view AS\n<body>` statement, with schema and view uppercased, matching the behaviour of `nz_get_table_ddl`. `tools-contract.md` updated. Closes #303.
- ES: **UX de la ejecución asíncrona** — `nz_call_procedure_async` ya no sugiere sondear "cada 30 s" fijo: devuelve `poll_after_s` (arranca en 2 s, crece con el tiempo transcurrido hasta un tope de 30 s) y `nz_job_poll` recalcula el mismo campo en cada sondeo, `null` cuando el job ya terminó. `session_id` sigue llegando `null` al lanzar (el hilo en segundo plano aún no abre la conexión); ahora la descripción y el hint lo explican en vez de dejarlo sin contexto. `nz_job_poll` documenta la diferencia entre `elapsed_ms` (reloj desde el lanzamiento, sigue creciendo) y `duration_ms` (lo que tardó el `CALL` dentro de Netezza, solo presente en `status == "done"`). `tools-contract.md` actualizado. Cierra issue #300.
- EN: **async execution UX** — `nz_call_procedure_async` no longer suggests a fixed "every 30 s" poll: it returns `poll_after_s` (starts at 2 s, grows with elapsed time up to a 30 s cap) and `nz_job_poll` recomputes the same field on every poll, `null` once the job has finished. `session_id` still comes back `null` at launch (the background thread hasn't opened the connection yet); the description and hint now explain why instead of leaving it unexplained. `nz_job_poll` documents the difference between `elapsed_ms` (wall clock since launch, keeps growing) and `duration_ms` (how long the `CALL` itself took inside Netezza, only present once `status == "done"`). `tools-contract.md` updated. Closes issue #300.
- ES: **`nz_execute_ddl` ya no reporta falso éxito al crear un SP con cuerpo NZPLSQL inválido** — Netezza compila los cuerpos NZPLSQL de forma perezosa: el servidor acepta el `CREATE` aunque el cuerpo sea inválido y el error solo aparece en el primer `CALL`. `nz_execute_ddl` ahora deja claro que `executed=true` significa "DDL aceptado", no "SP compilado": la respuesta siempre incluye `compile_warning` para `statement_type="procedure"`. El nuevo parámetro `validate_compile=true` emite un `CALL schema.proc(NULL::tipo, ...)` con placeholders tipados para forzar la compilación; el error queda en `compile_error` y `compiled=false`. `tools-contract.md` actualizado. Cierra #294.
- EN: **`nz_execute_ddl` no longer reports false success for an SP with invalid NZPLSQL body** — Netezza compiles NZPLSQL bodies lazily: the server accepts the `CREATE` even when the body is invalid and the error only surfaces on the first `CALL`. `nz_execute_ddl` now makes clear that `executed=true` means "DDL accepted", not "SP compiled": the response always includes `compile_warning` for `statement_type="procedure"`. The new `validate_compile=true` flag issues a `CALL schema.proc(NULL::type, ...)` with typed-NULL placeholders to force compilation; the error lands in `compile_error` and `compiled=false`. `tools-contract.md` updated. Closes #294.
- ES: **`nz_list_tables` ocultaba las tablas externas y `kind` era fijo** — `nz_list_tables` filtraba siempre `OBJTYPE='TABLE'` sin ningún parámetro para ver las `EXTERNAL TABLE`, así que un esquema con tablas externas (S3/archivos) las dejaba invisibles para cualquier inventario hecho con la tool. Ahora acepta `object_type` (`TABLE` default, `EXTERNAL TABLE`, `ALL`) y `kind` en el output refleja el `OBJTYPE` real de cada fila en vez de un valor fijo `"TABLE"`. `nz_describe_table` también fijaba `kind="TABLE"` sin mirar el catálogo: una vista descrita salía como `kind: TABLE` con `distribution: RANDOM`, aunque una vista no tiene distribución. Ahora resuelve el tipo real contra `_V_TABLE`/`_V_VIEW` (`TABLE`, `EXTERNAL TABLE` o `VIEW`) y omite la clave `distribution` cuando el objeto es una vista. Cierra issue #295.
- EN: **`nz_list_tables` hid external tables and `kind` was hardcoded** — `nz_list_tables` always filtered `OBJTYPE='TABLE'` with no parameter to see `EXTERNAL TABLE` rows, so a schema with external tables (S3/files) made them invisible to any inventory built with the tool. It now accepts `object_type` (`TABLE` default, `EXTERNAL TABLE`, `ALL`) and `kind` in the output reflects each row's real `OBJTYPE` instead of a fixed `"TABLE"` value. `nz_describe_table` also hardcoded `kind="TABLE"` without checking the catalog: describing a view came back as `kind: TABLE` with `distribution: RANDOM`, even though a view has no distribution. It now resolves the real type against `_V_TABLE`/`_V_VIEW` (`TABLE`, `EXTERNAL TABLE`, or `VIEW`) and omits the `distribution` key when the object is a view. Closes issue #295.
- ES: **descripciones honestas de las tools async** — `nz_call_procedure_async`: elimina mención a `nz_job_cancel` (diferida a #291); aclara que la cancelación no está disponible vía MCP (un DBA puede usar `nzsession` con el `session_id` de `nz_job_poll`). `nz_job_poll`: corrige afirmación de `partial_notices` durante ejecución (nzpy entrega `NOTICE` junto al resultset al terminar, no de forma incremental; `partial_notices` puede llegar vacío mientras el SP corre); documenta que el job store es en memoria y se pierde al reiniciar el servidor.
- EN: **honest async tool descriptions** — `nz_call_procedure_async`: removes mention of `nz_job_cancel` (deferred to #291); clarifies cancellation is not available via MCP (a DBA can use `nzsession` with the `session_id` from `nz_job_poll`). `nz_job_poll`: corrects `partial_notices` claim (nzpy delivers `NOTICE` with the resultset at completion, not incrementally; `partial_notices` may be empty while the SP is running); documents that the job store is in-memory and lost on server restart.

### Added

Si la columna tiene `MAX_ROWS_CAP` (1000) o más valores distintos, la llamada falla con `INPUT_TOO_BROAD` y un hint ("no parece una columna de partición") en vez de devolver un resumen parcial que un analista podría dar por bueno — mismo principio que #308. Identificadores validados y SQL pasado por `sql_guard`; un grupo `NULL` se devuelve como `value: null`. `tools-contract.md` actualizado. Cierra #338.
- EN: **new tool** — `nz_summarize_partitions` (`read` mode) summarizes rows per value of a partition/period column: returns one entry per value with its count (`partitions`), the total number of partitions (`partition_count`), the newest (`latest`) and the oldest (`earliest`), ordered newest first. It answers "did today's load land?" in one step without hand-writing the `GROUP BY` or sorting to find the latest partition, with `max_rows`/`truncated`/`hint` like the other listers (ADR 0018). Identifiers are validated and the SQL goes through `sql_guard`; a `NULL` group comes back as `value: null`. `tools-contract.md` updated. Closes #338.

- EN: **new tool** — `nz_compare_tables` (`read` mode) compares the schema of two tables or views, reporting columns exclusive to A (`only_in_a`), exclusive to B (`only_in_b`), data type/nullability mismatches (`type_mismatches`), and ordinal position mismatches (`position_mismatches`). Reads `_V_RELATION_COLUMN` in a single connection with cross-database support (optional `database_b` defaults to `database`; optional `schema_b` defaults to `schema_a`). Reports whether two structures are identical (`identical=true`) and streamlines layer validation and migrations without manual diffing between `nz_describe_table` calls. Closes issue #301.

- EN: **observable change** — `nz_table_sample` accepts optional `where` and `order_by` for targeted, reproducible samples (e.g. a segment by period), instead of the arbitrary sample that forced hand-writing `SELECT *` via `nz_query_select`. Both are raw SQL fragments: the composed statement is validated whole with `sql_guard.validate(mode="read")`, so a fragment with stacked statements, a non-`SELECT` kind or a mutation CTE is rejected (`GUARD_REJECTED`); the same-database guard and the `rows` cap stay intact. Closes issue #313.
- ES: **tools nuevas** — `nz_describe_view` y `nz_object_dependencies` (modo `read`). `nz_describe_view(database, schema, view)` describe las columnas/tipos de una vista (reusa `nz_describe_table`, que ya resuelve `kind=VIEW`) y añade `depends_on` con las relaciones que lee, derivadas parseando el `DEFINITION` de `_V_VIEW` con sqlglot y resolviendo el `kind` real de cada referencia contra `_V_TABLE`/`_V_VIEW`. `nz_object_dependencies(database, schema, object, direction="up"|"down", depth)` recorre el lineage en BFS: `up` sigue el `DEFINITION` de cada vista; `down` escanea los `DEFINITION` del esquema (Netezza no registra dependencias de vistas en `_V_DEPEND`, solo funciones/librerías) y conserva las que referencian el nodo. Hasta ahora "¿qué alimenta esta vista?" / "¿puedo cambiar esta tabla sin romper el reporte?" era abrir DDLs y parsear a ojo: `nz_find_table_references` solo cubre SPs. Las referencias cualificadas a otra base (`OTRA_BD.ESQ.TABLA`) se resuelven contra **esa** base y se exponen con su `database`, y la deduplicación del BFS usa `(database, schema, name)` para no colapsar una dependencia cross-database con un homónimo local. Until now "what feeds this view?" / "can I change this table without breaking the report?" meant opening DDLs and parsing by hand: `nz_find_table_references` only covers SPs. References qualified with another database (`OTHER_DB.SCHEMA.TABLE`) are resolved against **that** database and reported with their `database`, and the BFS de-duplicates by `(database, schema, name)` so a cross-database dependency is not collapsed onto a local homonym. ### Added
- ES: **cambio observable** — `remove-profile`, `init` y `add-profile` aceptan `--yes`/`-y`: responde "sí" a la(s) confirmación(es) de cada comando sin preguntar, para poder borrar o crear un perfil desde un script o CI. Sin `--yes`, si no hay terminal para preguntar (stdin cerrada, redirigida, CI), el comando ya no aborta con el "Aborted!" genérico de `click`: falla con exit code 1 y un mensaje traducido que sugiere `--yes`. Cubre también el camino más probable en CI: si la escalera de validación del asistente falla (típico sin VPN), `--yes` ya no cae en el cuarto prompt de "reintentar/corregir/guardar igual/cancelar" — guarda el perfil igual, sin preguntar, en vez de abortar. Cierra el hallazgo 2 de `docs/design/cli-redesign-proposal.md` (issue #274).
- EN: **observable change** — `remove-profile`, `init` and `add-profile` now accept `--yes`/`-y`: it answers "yes" to each command's confirmation(s) without asking, so a profile can be deleted or created from a script or CI. Without `--yes`, when there is no terminal to ask (closed or redirected stdin, CI), the command no longer aborts with `click`'s generic "Aborted!": it fails with exit code 1 and a translated message that points to `--yes`. Also covers the most likely CI shape: when the wizard's validation ladder fails (typical without a VPN), `--yes` no longer falls into the fourth "retry/fix/save anyway/cancel" prompt - it saves the profile anyway, without asking, instead of aborting. Closes finding 2 of `docs/design/cli-redesign-proposal.md` (issue #274).
- ES: **cambio de seguridad** — `nz_create_table`, `nz_create_table_as`, `nz_truncate`, `nz_drop_table`, `nz_drop_procedure` y `nz_drop_view` pasan ahora por la guarda de entorno `assert_env_safe`, que rechaza cualquier referencia `PROD_*` cuando el perfil activo no apunta a una BD `PROD_*` (código `PROD_REF_IN_NONPROD`). Hasta ahora esa guarda solo protegía `nz_call_procedure`, `nz_execute_ddl` y `nz_alter_table`; el resto de `catalog/ddl.py` podía crear, truncar o eliminar un objeto `PROD_*` desde un perfil de desarrollo sin ningún aviso. La guarda dispara **antes** de abrir conexión (incluso en `dry_run`, cuando la tool lo tiene), igual que en las tools que ya la usaban; no cambia nada para una BD/tabla que no empiece por `PROD_` (issue #278).
- EN: **security change** — `nz_create_table`, `nz_create_table_as`, `nz_truncate`, `nz_drop_table`, `nz_drop_procedure` and `nz_drop_view` now go through the environment guard `assert_env_safe`, which rejects any `PROD_*` reference when the active profile does not target a `PROD_*` database (`PROD_REF_IN_NONPROD` code). Until now that guard only protected `nz_call_procedure`, `nz_execute_ddl` and `nz_alter_table`; the rest of `catalog/ddl.py` could create, truncate or drop a `PROD_*` object from a development profile with no warning at all.
